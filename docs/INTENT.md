# INTENT

做一个实验管理系统，要让它有极强的 traceability，可以在多年后快速重新了解做该实验的**目的**、**结果**和**对后续调整的启发**。
它的底层依赖 git，只是针对实验场景和 agent 场景做一些重新设计，封装出一个更简单的心智模型，让用户和 agent 都好用。

名字：**ExpDeck**（命令行 `exp`，项目配置 `exp.toml`，本地缓存 `.exp/`，数据根 `.git/exp/`）

---

## 三个顶层需求

1. 不用人去管理各个实验，而抽象出一层接口（本软件），agent 可以通过本软件来管理各实验。
2. agent-friendly 是一等要求，所有设计要考虑到 agent 的快速使用与人力慢速做实验的区别，为多 agent 快速执行做针对性优化。
3. 需要有 web 界面，因为可以通过端口转发从实验服务器传到本地查看进度和成果（简单点即可，jupyter 风格就挺好）。

---

## 心智模型

用 exp 管理各种不同的实验——无论是搭模型过程中试验各种模块，还是模型搭好后的 baseline、消融实验。

统一抽象出这几个动作：

- `exp init`：摸清现有仓库结构并登记（写 `exp.toml`）。**已有 git 仓库直接解析；没有 git 不自动 init**，要显式 `--force` 才建——替用户 `git init` 是不可逆动作。
- `exp new`：新建分支并附一个工作树，在上面改代码，成为一个独立实验。
- `exp attach`：把一个分支变成工作树，方便并行训练、推理。
- `exp detach`：把一个工作树收回成普通分支。
- `exp run`：在工作树里跑一次实验，记录当前普通实验分支的提交和结果。运行前必须手动提交所有未忽略的改动；工作树不干净时拒绝运行，不自动提交。
- `exp note`：写笔记、写结论。

层级由分支路径决定：`exp/sensitive/hyperparameter` 在界面上就是三层文件夹。**文件夹只是路径前缀，不是实体。**

## agent-friendly

- 做成 CLI，agent 天然会用；skill / MCP 是后续的薄壳，不是主通道。
- 多 agent 并行靠 worktree；**同一实验内 run 串行**（工具加锁，不是靠自觉）。
- 唤醒机制：每个 run 伴随一个短命的监督进程，结束时把状态写进登记表；agent 用 `exp wait --run <id>` 阻塞等待，或由配置里的 hook 转发给框架。
- 硬约定：**agent 永远不直接操作 git**。绕过 `exp` 直接敲 git，就绕过了记录。

**关键判断：配置不是给用户写的，是给 agent 写的。** `exp init` 由 agent 读仓库后生成 `exp.toml`（启动命令、指标位置、产物位置），人只做 review。这是"人力配置负担太重"的解法——不是砍功能。

## web

web 主要为了人的**审阅**，同时是没有 agent 在场时的降级操作面。

**左侧栏（meta）**
- 实验树：解析 `exp/` 开头的分支与工作树，按 `/` 分层。运行中转圈；完成但未查看绿点；报错红点。
- 总图、总表：按各实验的结果数据做整体对比。

**中间（查看区）**
- 当前选中的实验 / run 的详情。

**右侧栏（标签区）**
- 标签由 `exp.toml` 的 `[cmds]` 生成：声明了 `plot`，右栏才有 plot；点击调用对应脚本，展示它的输出。
- 典型标签：改动（实时解析 main 与当前分支的 git diff）、进度（进度条 + 日志流）、曲线（解析 tensorboard log）、结果（图与表）。

**底部**
- 运行按钮：长命令点了就进入监视状态——按钮变灰并出现中断按钮。任务完成或中断都会写进记录。

**明确不做**
- 任何**代码**编辑区（没有跳转查找、没有语言服务）。平台只提供两样东西：执行约定位置的脚本并显示输出；一个纯文本的笔记编辑框。
- 参数的提取与编辑。很多参数藏在代码里，工具不去理解它们，只记录实际执行的命令。

**其他**
- 支持结果、日志下载到本地；支持多选批量导出。

## 已定决策

| # | 决策 | 日期 |
|---|---|---|
| 1 | 实验是容器，可含多个**串行** run；实验之间并行 | 11-11 |
| 2 | 每个 run 记录普通实验分支当前提交；run 的 diff = 上次 run 的提交 → 本次提交；首次对比实验创建时的起点 | 11-26 |
| 3 | 实验有两个指针：`head`（最近 valid）、`best`（按主指标最佳） | 11-11 |
| 4 | 不同假设 = 不同实验；扫参 = 同文件夹下多个并行实验 | 11-11 |
| 5 | 一律异步；每 run 一个监督进程，结束写登记表 | 11-11 |
| 6 | 记状态靠实时解析 + 登记表缓存，不靠"先写记录" | 11-11 |
| 7 | web 可以触发任何命令（运行中按钮变中断），不限只读 | 11-11 |
| 8 | `eval` 只给已有 run 补指标，不产生新 run | 11-11 |

## 非目标

- 不是 tracking server，不做多机、多人、云端调度
- 不是 W&B / MLflow 的替代品，可导出但不竞争
- 不是数据版本管理（DVC 那一层）
- 不是 IDE、不是 notebook
- 不做图表交互探索那种 dashboard

## 判据

- **规模假设决定了所有取舍。** 单个项目十几个实验，二三十个算多，五十个顶天（不含已删的）；每个实验几次到几十次 run。所以不索引、不分页、不缓存。
- **`.exp/` 里所有东西删掉都不心疼。** 有价值的实验记录放在 `.git/exp/`，一次性的挂 run，缓存才算 `.exp/`；记录的迁移暂不考虑。
- **记录便宜、权重贵。** 实验记录保留在本地 `.git/exp/`；权重可能很大，单独作为产物管理。
- **能重算的绝不存。** 已提交的 diff 实时算；未提交的代码先手动提交再运行。
- **不引入数据库。** 记录就是文件树，查询现算；真要缓存，也只能是删了能自动重建的派生物。
